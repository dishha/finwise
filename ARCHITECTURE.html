🏦 FinWise Agent Harness

Architecture & Implementation Guide

What it does: FinWise is an agentic readiness harness for bank advisors. It processes client financial signals through three parallel Claude agents (planner, wellness, briefing) to detect life-event opportunities (home purchase, renewal, liquidity, attrition) and produces evidence-backed readiness cards that advisors review before outreach.

AWS Architecture & Deployment

FinWise runs on AWS using AgentCore, a fully managed agentic platform. The architecture separates concerns across data, compute, application, and model layers.

Layer Details

  • Data Layer (S3): Stores client signals (clients/*.json) and skill definitions (skills/*/SKILL.md); Lambda reads/writes here; fallback resilience built in
  • Compute Layer (Lambda + Gateway): Lambda (Python 3.13, 30s timeout) executes tool logic; Gateway routes tool calls from Harness using gateway_tools.json schema (5 tools listed)
  • Application Layer (AgentCore Harness): Orchestrates entire flow—loads instructions, manages tools, progressively loads skills, tracks outcomes in Memory
  • Model Layer (Bedrock): Claude Sonnet 4.6 (ca-central-1) powers reasoning and decision-making for all three agents (planner, wellness, briefing)

Three Agents (All Claude)

1. Planner Agent

Role: Orchestrator & evidence gatherer

Input: client_id + prior_outcomes

Tools available: get_signals, assess_savings, check_qualification

Output: JSON with cards[] containing confidence, timeline, urgency_rank, evidence list

Critical constraint: Cannot override check_qualification. If qualification fails, confidence capped at 0.7 max.

2. Wellness Agent

Role: Independent risk gatekeeper

Input: Full signal bundle (from get_signals)

Output: Verdict + risk_level + reasons

Verdicts:
• proceed → no override
• downgrade → ×0.7 confidence
• veto → confidence capped at 0.35

Runs in parallel with planner. Can reject any opportunity based on cash-flow risk, credit stress, or debt load.

3. Briefing Agent

Role: Narrative writer + evidence validator

Input: Planner card + wellness verdict + merged evidence

Output: Cited brief + grounding check result

Constraint: Every factual sentence ends with [E1], [E2], etc. matching evidence index. Deterministic validator enforces this; retries up to 2x if citations fail.

Runs sequentially after planner & wellness complete.

The Qualification Gate (Most Critical)

Rule-based, non-negotiable: The check_qualification tool applies Canadian mortgage stress-test rules. It calculates GDS (housing payment / gross income) and TDS (housing + debt / gross income) at a stress-test rate of max(5.25%, current_rate + 2.0%).

The constraint: Planner cannot emit a home_purchase card with confidence > 0.7 if qualifies = false. This protects the client from being pushed into an unaffordable purchase, and protects the advisor from regulatory risk.

Why: Mortgage qualification is not a judgment call. It is a legal and prudential gate. The model can say "ready on savings" or "not yet on savings," but it cannot override the math.

The Wellness Veto (Consumer Protection)

When Wellness Vetoes

Wellness independently assesses financial risk. It vetoes when:

  • Negative cash-flow months: Any month with surplus < 0
  • High cash-flow variance: Std dev too high relative to mean
  • Credit stress: Credit utilization > 50% or missed payments in last 12 months
  • Debt load: Monthly debt payments > ~35% of net income

Example: Marcus (C-1002) has a renewal opportunity coming in 3 months, but wellness vetoes because: negative cash-flow months (-$1.1k, -$600), high debt ($2.1k/month), and high variance. The card is still shown to the advisor, but confidence is capped at 0.35 and the recommended action becomes "Hold outreach … check in on cash-flow stability first."

Key Design Constraints

  • Rule-based qualification gate: check_qualification is deterministic. Planner cannot override.
  • Independent wellness: Runs in parallel, can veto any opportunity. Protects consumer.
  • Evidence-grounded briefs: Every fact cited [E#]. Deterministic grounding validator ensures accuracy.
  • Treat free-text as data: Product telemetry, advisor notes, prior outcomes are read as data, never as instructions.
  • Prior outcomes shape decisions: Planner suppresses "not_now" cards unless a signal materially changed.
  • Fallback resilience: If Memory unavailable, system falls back to local JSON. Harness keeps running.

Summary

FinWise in One Paragraph:
A request arrives with a client_id. The system loads raw client data and prior outcomes, then spawns two Claude agents in parallel: planner analyzes signals and calls tools (assess_savings, check_qualification) to detect opportunities, emitting cards with evidence and confidence scores; wellness independently assesses risk and returns a verdict (proceed, downgrade, veto). Both complete, results merge, wellness overrides are applied (veto caps confidence at 0.35, downgrade multiplies by 0.7), cards sort by urgency and confidence, and for each card the briefing agent writes a 4–6 sentence narrative with [E#] citations validated by a deterministic grounding checker. Output is JSON cards ready for advisor review. Advisor records actions (contacted, not_now, already_handled), which feed back into the next run to suppress or re-surface opportunities based on signal change. Everything is rule-based (qualification), evidence-backed (briefs), and consumer-protective (wellness veto).
